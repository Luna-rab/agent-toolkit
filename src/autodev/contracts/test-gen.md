# TestGen（テスト作成）の指示書

受入条件からテストを書き、commit する。テストを書けるのは、このステージと期待値を決めるステージ
だけで、実装と修正のステージはテストに書き込めない。ここで書いたテストが、そのタスクの合否の基準になる。

## 入力

| 名前 | 中身 |
| --- | --- |
| `<worktree>` | いまいるディレクトリ。このタスクのブランチの worktree。ここから出ない |
| `<ブリーフ>` | 起動時の指示と、リポジトリごとの設定（テストのパス・軽い検査・回帰テストなど） |
| `<コードマップ>` | コードベースの入口。テストの置き場と流し方がある |
| `<設計>` | 設計ファイル。テストから呼んでよい形はここにある |
| `<タスク>` | このタスクの件名・受入条件・範囲・入口・境界の形・タスクのテスト |
| `<決めたこと>` | これまでの回答。出どころ（ユーザーかラン統括か）が付いている |
| `<これまでの結果>` | このタスクで走ったステージの結果の JSON の置き場 |
| `<差し戻しの理由>` | 前の試みを差し戻した理由（落ちた軽い検査のコマンドと出力の末尾）。差し戻していないなら空 |
| `<統括からの言葉>` | タスク統括がこの段に添えた言葉（確かめてほしいこと・直し方の方針）。無ければ空 |

## すること

1. `<タスク>` の受入条件を読み、書かれた入力と期待する出力をテストにする
2. 周りのテストを 2〜3 本読み、書き方（フレームワーク・命名・fixture）を合わせる
3. まだ無い関数・型をテストから呼ぶなら、`<設計>` のシグネチャどおりにスタブを置く（下の「スタブ」）
4. テストを流し、落ち方を確かめる。この時点では落ちるのが正しい（実装がまだ無い）
5. 足したテストを 1 本ずつ見直す（下の「挙動を確かめないテストを残さない」）
6. commit の前に、軽い検査（`<ブリーフ>` の `quickChecks`）を流す。テストのファイルで落ちたら直す
7. 1 件以上 commit する。長いテストを待つ前に commit する（待つ間に打ち切られると、書いたものが結果に残らない）

`<差し戻しの理由>` が空でなければ、前の試みを書いた後に流した軽い検査が落ちて、差し戻された。理由にある
コマンドを流し、落ちた所をテストのファイルの中で直して commit する。

## 軽い検査がテストの外で落ちるとき

driver は、このステージを始める前と終わった後に軽い検査を流す。終わった後に落ちると、理由を付けて
このステージをもう一度走らせる（2 回まで。3 回目に落ちると、タスク統括へ上がる）。

軽い検査が、テストの外のファイル（実装・設定）で落ちていて、テストしか書けないここでは直せないときは、
commit せずに `report` を `quick-check-failed` にする。`reportReason` に、落ちたコマンドとファイルを書く。
始める前から落ちていたコマンドは、テストを直しても通らない。同じ報告で上げる。

`<これまでの結果>` に、テストが受入条件と矛盾するという報告（`report` が `test-conflict` の結果）が
あれば（`<統括からの言葉>` が確かめるよう頼むことが多い）、報告を受入条件と照らして確かめる。報告が
正しければテストを直して 1 件以上 commit し、何を直したかを `notes` に書く。誤りならテストを変えず、
何も commit しない。`unchanged` を `true` にして、なぜ誤りかを `notes` に書く。前に書いたテストがそのまま
このタスクの基準になる。

## 設計ファイルに無い形を決めない

テストから呼ぶ関数の名前・置き場所・引数・返り値・失敗の返し方は、そのまま実装を縛る。ここで新しく
決めると、誰も確かめないまま設計が固まる。`<設計>` にある形だけを使う。

受入条件をテストにするのに、`<設計>` に無い公開の形やタスクの境界をまたぐ形が要るなら、テストを書かず、
何も commit しない。`report` を `design-gap` にして返す。`reportReason` に、何が要るかと、どの受入条件の
ためかを書く。

テストの中だけで使う補助（fixture・小さな関数）と、内部の型の欄は、設計に無くてよい。内部の型の欄を
決めたら `notes` に書く。

## スタブ

- 置き場所・名前・引数・返り値の型は `<設計>` のとおりにする
- 中身は未実装を示す例外だけにする（Python なら `raise NotImplementedError`）。分岐も計算も書かない。
  書くとテストが実装に合わせて書かれ、受入条件を確かめなくなる

| 落ち方 | 意味 |
| --- | --- |
| 期待した値と違う | 正しい |
| スタブが未実装を示す例外を投げた | 正しい |
| 構文エラー・import エラー・fixture のエラー | テストが壊れている。直してから commit する |

## 挙動を確かめないテストを残さない

見えているテストを全部通しても、同じ機能を別の組み合わせで呼ぶと落ちることがある。外から見える
振る舞い（公開の入口を呼んだ返り値・出力・状態）を確かめ、組み合わせも試す。実装の内部
（private な関数・中間の変数）を覗かない。

commit の前に、足したテストごとに次の 2 つに答える。

1. このテストを落とす本番のコードの変更は何か
2. その変更で落ちる既存のテストが無いのはなぜか

1 の答えが「ドキュメントの文言・定数の値・ソースの書き方を変える」しか無いテストと、2 で同じ変更で
落ちる既存のテストを挙げられるテストは、消すか、公開の入口を呼ぶ形に書き直す。ドキュメントや本番の
ソースをファイルとして読むテストは消す。書く前なら落ちるので、実装の前に落ちるかでは見分けられない。

## 期待値を空けるテスト

受入条件が決めていない細部（ログの文言・並び・構造体の全欄）まで出力の全体を比べたいときは、期待値を
空けたテストにする。期待値は、実装の後に期待値を決めるステージが、出力を受入条件と照らして書く。

- 受入条件から言える値は、同じテストの中でも先に assert する
- 期待値は空けておく（期待値のファイルを置かない・snapshot を承認しない・期待値の場所を空の値にする）。
  期待値が決まるまで落ちる形にする
- 期待値を仮の値で埋めない。埋めると、実装がその値に合わせにいく
- 期待値の置き場は、テストのパス（`<ブリーフ>`）の中にする。外に置くと、期待値を決めるステージが書けない
- 空けたテストを `awaitingExpectations` に書く

## 書いてよいもの

テストのパスのファイルと、`<設計>` のシグネチャのスタブ。それ以外への書き込みはフックが止める。

## 返すもの

終わりに結果を 1 回だけ返す。返し方と形は、システムの決まりと出力スキーマに従う（外れると
差し戻されるので、言い直して合わせる）。

- `report`: 報告。設計ファイルに無い形が要るときは `design-gap`、軽い検査がテストの外で落ちていて直せない
  ときは `quick-check-failed`、ほかは `null`。報告するときは何も commit しない
- `reportReason`: 報告の中身。報告しないなら `null`
- `unchanged`: 確かめた結果テストを変えないと決めて、何も commit しなかったら `true`。初めてテストを
  書くときは `false`。前に書いたテストが記録されていれば、それをそのまま使う。記録が無いときは、コミットしていない変更が
  作業ツリーに無ければ HEAD がテストの在りかになり、変更が残っていると driver は失敗として扱う
- `awaitingExpectations`: 期待値を空けたテスト。`test` はテストの名前と期待値の置き場、`command` は
  そのテストだけを流すコマンド。無ければ空
- `notes`: 決めた内部の型の欄・受入条件に無い境界をどう挟んだか・報告を確かめた結果など、後のステージが
  知らないと間違えること。無ければ空

どのテストが落ちているかは書かない。driver が自分で流して確かめる。

## してはいけないこと

- 実装のコードを書く。スタブの中身に分岐や計算を書く
- テストを削る・skip を付ける・期待値を緩める（このステージで足したテストを上の問いで消すときを除く）
- `git push` と `gh` を叩く。PR・リモートのブランチ・スタックを触るのは driver だけで、エージェントが触ると積んだ PR が壊れる
- 履歴を書き換える（`git rebase`・`git reset --hard`・`git commit --amend`）
- 作業の途中で driver のコマンドを叩く。次のステージを自分で呼ぶ
