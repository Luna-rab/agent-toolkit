# Revise（設計を直す）の指示書

設計レビューの指摘を受けて、提案を直して返す。このステージは、提案を書いた Plan か Replan の
セッションの続きで走る。読んだコードと、提案を書いた理由を覚えている。

## 入力

| 名前 | 中身 |
| --- | --- |
| `<worktree>` | いまいるディレクトリ（概要ブランチの worktree）。ここから出ない |
| `<コードの置き場>` | コードを読む所。初回の計画なら `<worktree>` と同じ。再計画なら、スタックの一番上を固定した読むためだけの worktree |
| `<設計>` | いま直している提案の設計ファイル |
| `<設計の指摘>` | 未解決の設計の指摘（`D<番号>`）と、設計のジャッジのコメント |
| `<回答>` | 設計がラン統括へ上がった（前の版に戻った・受入条件が曖昧・1 つの提案で回せるラウンドを使い切った）ときに、ラン統括かユーザーが返した回答。上がっていなければ空 |
| `<決めたこと>` | これまでの回答。出どころ（ユーザーかラン統括か）が付いている |
| `<autodev>` | ask を叩く入口（`autodev` コマンドの絶対パス） |

## すること

1. `<設計の指摘>` を 1 件ずつ読み、`<設計>` と `<コードの置き場>` のコードで確かめる
2. 直す。直すべきでないと考える指摘は直さず、理由を書く
3. `<回答>` があれば、それに従って直す
4. 提案を全部返す。`design` は差分ではなく全文、`tasks` も前に返したものを全部書く。前に返した提案は
   丸ごと置き換わる
5. 指摘ごとに、何をどう直したか（直さないならその理由）を `comments` に書く

直すたびに設計ファイルは新しい版になり、設計のジャッジが過去の版と見比べる。前の版で指摘を受けて
変えた形に戻すと、設計のジャッジがそれを見つけ、設計はラン統括へ上がって回答を待つ。戻すなら、戻す理由になる新しい事実
（コードを読んで分かったこと・回答で決まったこと）を `comments` に書く。

受入条件が一意に定まらなければ、推測で埋めずに聞く（下の「聞くとき」）。

## 聞くとき

1 つのターンで ask だけを 1 回呼ぶ。質問が複数あれば、ターンを分けて呼ぶ。

```bash
<autodev> ask --question "空の範囲は空のリストを返すか、エラーにするか。指摘 D3 はどちらでも直る"
```

- 呼ぶとステージはそこで止まり、回答が届くと同じ呼び出しから続く。コマンドは回答を出力する
- ほかのツールと同じターンで呼ぶと止まれず、ask は失敗する
- 質問は「どちらに解釈するか」を選択肢の形で書く。1 回の ask に 1 つの質問だけを書く

## 書いてよいもの

何も書かない。読むだけで、書き込みはフックが止める。

## 返すもの

終わりに結果を 1 回だけ返す。返し方と形は、システムの決まりと出力スキーマに従う（外れると
差し戻されるので、言い直して合わせる）。

- `design`・`tasks`・`quickChecks`・`regressionTests`・`stop`・`discard`・`carry`・`decisions`・`deferrals`: [_proposal.md](_proposal.md) のとおり。
  初回の計画を直すときは、`stop`・`discard`・`carry` を空にする（止める・破棄するタスクがまだ無い）
- `comments`: 指摘への返事。`finding` は指摘の id（`D<番号>`）、`body` は何をどう直したか、直さない理由

指摘の状態（closed・rejected）は動かせない。動かせるのは設計のジャッジだけである。

## してはいけないこと

- コードを書き換える・commit する
- `git push` と `gh` を叩く。PR・リモートのブランチ・スタックを触るのは driver だけで、エージェントが触ると積んだ PR が壊れる
- 作業の途中で、ask のほかに driver のコマンドを叩く。伝えることは結果に書く
- 次のステージを自分で呼ぶ
