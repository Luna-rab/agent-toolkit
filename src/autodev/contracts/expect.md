# Expect（期待値を決める）の指示書

テストを書いたときに期待値を空けたテストに、実装の出力を受入条件と照らして期待値を書き、commit する。
出力を写すだけの承認にしない。

## 入力

| 名前 | 中身 |
| --- | --- |
| `<worktree>` | いまいるディレクトリ。このタスクのブランチの worktree。ここから出ない |
| `<ブリーフ>` | 起動時の指示と、リポジトリごとの設定（テストのパス） |
| `<タスク>` | このタスクの件名・受入条件・範囲 |
| `<決めたこと>` | これまでの回答。出どころ（ユーザーかラン統括か）が付いている |
| `<期待値待ちのテスト>` | 期待値を空けたテストと、そのテストだけを流すコマンド |

## すること

1. `<期待値待ちのテスト>` のコマンドを流し、実装の出力を得る。リポジトリに期待値を更新する仕組み
   （`cargo insta`・`UPDATE_GOLDEN=1`・`jest -u` など）があれば使ってよい
2. 出力を 1 件ずつ、受入条件とテストのシナリオの意図に照らして確かめる。数・順序・状態の変化のように
   受入条件に照らせる箇所は、照らしてから書く。受入条件が決めていない細部（文言・並び）は、実装が
   決めたものとして受け入れてよい
3. 合っている出力だけを期待値として書く
4. 受入条件と食い違う出力は期待値にしない。`defects` に書く。1 件ずつ、このステージを出どころとする
   must-fix の指摘になり、同じラウンドのジャッジが判定して、修正のステージが実装を直す
5. 期待値を書かなかったテスト（`defects` に挙げたテストを含む）は、期待値を空けたまま `awaitingExpectations`
   に残す。残っている間、次のラウンドの頭でこのステージがもう一度走り、直した実装の出力を確かめる
6. 期待値を 1 つでも書いたら commit する。1 つも書かなければ commit しない

テストのシナリオ（入力・操作・要所の assert）は変えない。シナリオが受入条件と矛盾すると考えたら、
変えずに `report` を `test-conflict` にして返す。期待値を決めるのに、設計ファイルに無い形が要るなら
`design-gap` にして返す。報告するときは何も commit しない。

## 書いてよいもの

テストのパスのファイルだけ。それ以外への書き込みはフックが止める。

## 返すもの

終わりに結果を 1 回だけ返す。返し方と形は、システムの決まりと出力スキーマに従う（外れると
差し戻されるので、言い直して合わせる）。

- `report`: 報告。`test-conflict`・`design-gap` のどちらかを報告するときだけ書き、ほかは `null`
- `reportReason`: 報告の中身。報告しないなら `null`
- `written`: 期待値を書いたテスト
- `awaitingExpectations`: まだ期待値を書いていないテスト（`defects` に挙げたテストなど）。形は
  `<期待値待ちのテスト>` と同じで、`test` はテストの名前と期待値の置き場、`command` はそのテストだけを
  流すコマンド。全部書いたら空
- `defects`: 期待値にしなかった出力。`test` はテストのファイルと名前（`tests/test_report.py::test_render`
  の形。指摘の位置になる）、`output` はどの出力が、`acceptance` は受入条件のどの記述と、どう食い違うか。
  無ければ空

## してはいけないこと

- 実装のコードを書き換える
- テストのシナリオを変える・テストを削る・skip を付ける
- `git push` と `gh` を叩く。PR・リモートのブランチ・スタックを触るのは driver だけで、エージェントが触ると積んだ PR が壊れる
- 履歴を書き換える（`git rebase`・`git reset --hard`・`git commit --amend`）
- 作業の途中で driver のコマンドを叩く。次のステージを自分で呼ぶ
