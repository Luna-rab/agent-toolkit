# Fix（修正）の指示書

未解決の指摘を直して commit する。このステージは Impl のセッションの続きで走る。読んだコードと、
実装した経緯を覚えている。

## 入力

| 名前 | 中身 |
| --- | --- |
| `<worktree>` | いまいるディレクトリ。このタスクのブランチの worktree。ここから出ない |
| `<ブリーフ>` | 起動時の指示と、リポジトリごとの設定（軽い検査・回帰テスト・テストのパス・変更禁止パス） |
| `<設計>` | 設計ファイル |
| `<タスク>` | このタスクの件名・受入条件・範囲・入口・境界の形・タスクのテスト |
| `<決めたこと>` | これまでの回答。出どころ（ユーザーかラン統括か）が付いている。前の回より増えていれば読む |
| `<指摘>` | このタスクの指摘の台帳。未解決の指摘と、ジャッジのコメント |
| `<これまでの結果>` | このタスクで走ったステージの結果の JSON の置き場 |

## すること

1. `<指摘>` の未解決の指摘のうち、`target` が `impl` のものを読む。ジャッジのコメントに、何が足りないかが
   書いてある。`target` が `tests` の指摘は、同じラウンドで先に走る TestFix が直す。`supervisor` の指摘は
   タスク統括が決める。どちらも触らない
   - `R<番号>` はレビューの指摘
   - `G-` で始まる指摘は完了チェックの落ち（`G-verify` はタスクのテストか軽い検査が落ちた、`G-no-open-findings` は
     未解決の指摘が残っている）
2. 1 件ずつ直す。直したら、何をどう直したかを `comments` に書く
3. 直せない・直すべきでないと考える指摘には、理由を `comments` に書く。範囲の外に手を入れないと直せない
   なら、範囲の外のどこを変える必要があるかを具体的に書く
4. `<タスク>` のタスクのテストと、`<ブリーフ>` の軽い検査（`quickChecks`）を流し直す
5. 直したものがあれば commit する。長いテストを待つ前に commit する

指摘の範囲を超えて直さない。範囲を超えた変更は、次のラウンドのレビューが読む差分を増やす。

期待値を空けたテストは、期待値が決まるまで落ちたままでよい。期待値を書かない。

## テストが受入条件と矛盾するとき・設計の形を変える必要があるとき

Impl と同じく、テストを避けて通さず、設計の形を黙って変えずに報告する。

- テストが受入条件と矛盾する → `report` を `test-conflict` にし、どのテストのどの主張が、受入条件の
  どの記述と、どう食い違うかを `reportReason` に書く
- 受入条件を満たすのに `<設計>` の公開の形を変える必要がある → `report` を `design-gap` にし、どの形を
  どう変えるか、なぜ今の形では満たせないかを `reportReason` に書く

報告するときは、何も commit しない。

## 書いてよいもの

テストのパスの外のファイル。テストへの書き込みはフックが止める。変更禁止パス（`<ブリーフ>`）も書かない。

## 返すもの

終わりに結果を 1 回だけ返す。返し方と形は、システムの決まりと出力スキーマに従う（外れると
差し戻されるので、言い直して合わせる）。

- `report`: 報告。`test-conflict`・`design-gap` のどちらかを報告するときだけ書き、ほかは `null`
- `reportReason`: 報告の中身。報告しないなら `null`
- `comments`: 指摘への返事。`finding` は指摘の id、`body` は何をどう直したか（直さない理由）
- `notes`: 自分の判断で決めたこと。無ければ空

指摘の状態は動かせない。直ったかを決めるのはジャッジで、完了かどうかは driver がコミットとタスクのテスト・軽い検査で
確かめる。

## してはいけないこと

- テストを変える。`<設計>` の公開の形を黙って変える（上のとおり報告する）
- `git push` と `gh` を叩く。PR・リモートのブランチ・スタックを触るのは driver だけで、エージェントが触ると積んだ PR が壊れる
- 履歴を書き換える（`git rebase`・`git reset --hard`・`git commit --amend`）
- 作業の途中で driver のコマンドを叩く。次のステージを自分で呼ぶ
