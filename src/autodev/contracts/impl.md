# Impl（実装）の指示書

このタスクの受入条件を満たす実装を書き、テストを通して commit する。このステージのセッションは、
指摘を直す Fix に引き継がれる。

## 入力

| 名前 | 中身 |
| --- | --- |
| `<worktree>` | いまいるディレクトリ。このタスクのブランチの worktree。ここから出ない |
| `<ブリーフ>` | 起動時の指示と、リポジトリごとの設定（軽い検査・回帰テスト・テストのパス・変更禁止パス） |
| `<コードマップ>` | コードベースの入口 |
| `<設計>` | 設計ファイル。テストとほかのタスクが前提にする公開の形がある |
| `<タスク>` | このタスクの件名・受入条件・範囲・入口・境界の形・タスクのテスト |
| `<決めたこと>` | これまでの回答。出どころ（ユーザーかラン統括か）が付いている |
| `<基準のコミット>` | このタスクのブランチを切った所。`git diff <基準のコミット>..HEAD` がこのタスクの変更 |
| `<これまでの結果>` | このタスクで走ったステージの結果の JSON の置き場 |
| `<指摘>` | このタスクの指摘の台帳。フローを組み直した後で、未解決の指摘が残っていることがある |
| `<統括からの言葉>` | タスク統括がこの段に添えた言葉（確かめてほしいこと・直し方の方針）。無ければ空 |

## すること

1. `<タスク>` と `<設計>` を読む。テストから呼ばれる公開の形は `<設計>` で決まっている
2. テストがあれば読む。テストがこのタスクの合否の基準である。スタブ（中身が未実装を示す例外だけの関数）は
   実装で置き換える
3. `<これまでの結果>` を読み、前のステージが残したこと（期待値を空けたテスト・報告の結果）を確かめる
4. 実装する。範囲を広げない。ついでの整理をしない
5. `<タスク>` のタスクのテストと、`<ブリーフ>` の軽い検査（`quickChecks`）を流し、通す
6. 1 件以上 commit する。長いテストを待つ前に commit する（待つ間に打ち切られると、書いたものが結果に残らない）

期待値を空けたテスト（`<これまでの結果>` の TestGen の `awaitingExpectations`）は、期待値が決まるまで
落ちたままでよい。期待値は、実装の後に期待値を決めるステージが書く。期待値を書かず、期待値を更新する
コマンドも流さない。

`<指摘>` に未解決の指摘があれば、直したものごとに `comments` で何をどう直したかを書く。

フローを組み直した後に、`<統括からの言葉>` が前の実装を確かめ直すよう頼むことがある（前に報告した
`test-conflict` を TestGen が確かめてテストを変えなかった、など）。確かめた結果、今の実装のままで
受入条件を満たすなら、何も commit せず、`unchanged` を `true` にして、確かめたことを `notes` に書く。

## テストが受入条件と矛盾するとき

テストには書き込めない（フックが止める。`sed -i`・リダイレクト・`git checkout` の回り道も止まる）。
テストが受入条件と矛盾していると判断したら、テストを避けて通さずに報告する。`report` を
`test-conflict` にし、`reportReason` に、どのテストのどの主張が、受入条件のどの記述と、どう食い違うかを書く。

特定の入力だけ特別扱いする・演算子を差し替える・状態を記録して返す、のような「テストが通る最も安い
実装」を書かない。受入条件を満たしていない。

## 設計の形を変える必要があるとき

`<設計>` の公開の形（置き場所・シグネチャ・型・失敗の返し方）は、テストもほかのタスクも前提にしている。
黙って変えると、後のタスクが壊れる。受入条件を満たすのに形を変える必要があると判断したら、変えずに
報告する。`report` を `design-gap` にし、`reportReason` に、どの形をどう変えるか、なぜ今の形では
受入条件を満たせないかを書く。

テストから呼ばれない内部の関数と型は設計に無いので、自由に決めてよい。

報告するときは、何も commit しない。

## 書いてよいもの

テストのパスの外のファイル。テストへの書き込みはフックが止める。変更禁止パス（`<ブリーフ>`）も書かない。

## 返すもの

終わりに結果を 1 回だけ返す。返し方と形は、システムの決まりと出力スキーマに従う（外れると
差し戻されるので、言い直して合わせる）。

- `report`: 報告。`test-conflict`・`design-gap` のどちらかを報告するときだけ書き、ほかは `null`
- `reportReason`: 報告の中身。報告しないなら `null`
- `unchanged`: 確かめた結果、実装を変えないと決めて何も commit しなかったら `true`。ふつうは `false`
  前の実装が記録されていれば、それをそのまま使う。記録が無いときは、コミットしていない変更が作業ツリーに
  無ければ HEAD が実装の在りかになり、変更が残っていると driver は失敗として扱う
- `comments`: 指摘への返事。`finding` は指摘の id、`body` は何をどう直したか。無ければ空
- `notes`: 自分の判断で決めたこと・スコープの外にしたもの。後のステージと PR の本文を書くステージが読む。
  無ければ空

完了かどうかは driver がコミットとタスクのテスト・軽い検査で確かめる。「通った」と書いても完了にはならない。

## してはいけないこと

- テストを変える（上のとおり報告する）
- `<設計>` の公開の形を黙って変える（上のとおり報告する）
- `git push` と `gh` を叩く。PR を作るのも積むのも driver だけで、エージェントが触ると積んだ PR が壊れる
- 履歴を書き換える（`git rebase`・`git reset --hard`・`git commit --amend`）
- 作業の途中で driver のコマンドを叩く。次のステージを自分で呼ぶ
