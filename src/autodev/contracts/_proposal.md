# 提案の書き方（Plan・Replan・Revise）

Plan・Replan・Revise は、どれも提案を返す。提案は設計レビューを通ってから反映され、反映されると
タスクが動き出す。このファイルは、提案の各キーの意味と、書くときに知らないと間違えることだけを書く。
形（型・必須）は出力スキーマにある。

## 1. キーの意味

| キー | 意味 |
| --- | --- |
| `design` | 設計ファイルの全文（Markdown）。driver が新しい版として書き出し、テストを書くステージから後が読む。差分ではなく全文を書く |
| `tasks` | タスクの一覧（下の 2.） |
| `quickChecks` | ラン共通の軽い検査（lint・型検査のように速いもの）。実装タスクの完了チェックと、タスクを積む直前の統合検査で流す |
| `regressionTests` | ラン共通の回帰テスト（テスト全体のように遅いもの）。タスクを積む直前の統合検査でだけ、スタックの一番上へ rebase した後で流す |
| `stop` | 止める実装タスクの id。確定した設計がある再計画だけが書く |
| `discard` | 破棄する積んだタスクの id。確定した設計がある再計画だけが書く。再利用できない理由を `design` に書く |
| `carry` | 未解決の指摘を別のタスクへ移す。`finding` は指摘の id、`fromTask` は今の持ち主、`toTask` は移す先 |
| `decisions` | 自分の判断で決めたこと（割り方を選んだ理由・指示が決めていなかった値など）。概要 PR の判断ログに載る |
| `deferrals` | スコープの外にしたもの。概要 PR に載る |

`decisions` と `deferrals` は、起動時の指示を読んでいない人が PR で読む。指示や受入条件を番号で指さず、
中身を書く。

## 2. タスク

タスク 1 つが 1 つのブランチと 1 つの PR になり、PR は 1 本の線のスタックに積まれる。`blockedBy` に
挙げたタスクがすべて積まれたタスクから始まり、互いに依存しないタスクは並列に走る。

初回の計画（Plan と、それを直す Revise）で、指示を満たすのに変更が要らないと分かったら、`tasks` を
0 件で返してよい。そのときは PR を 1 本も作らずにランを終える。再計画（Replan と、それを直す Revise）の
`tasks` は足す・変えるタスクだけなので、0 件でもよい。

| キー | 意味 |
| --- | --- |
| `id` | `task<番号>`。残すタスクは今の id。新しいタスクは、ランで使ったどの番号（止めた・破棄したタスクの番号も含む）よりも大きい番号（初回の計画は `task1` から） |
| `title` | PR のタイトルになる。何をするかが 1 行で分かる形 |
| `dod` | 達成すべき状態。「何が動くか」で書く |
| `acceptance` | 受入条件。テストを書くステージは、これを見てテストを書く |
| `scope` | 触る範囲と、触らない範囲 |
| `entryPoints` | 最初に読むファイルと関数（`path:行` の形） |
| `boundary` | このタスクが作り、ほかのタスクが使う形（型・関数の名前）。詳しい形は `design` に書き、ここには何をどのタスクが使うかを 1〜2 行で書く |
| `taskTests` | このタスクのテストを流すコマンド。テストが実装の前に落ちることの確かめと、完了チェックで流す |
| `blockedBy` | 積まれるのを待つタスクの id |

### 受入条件

- 入力と期待する出力を具体値で書く。テストを書くステージが読むのはこれだけで、曖昧な基準はそのまま
  誤った合否になる
- 設計ファイルからではなく、指示から書く。「この形の値が返る」しか書けない受入条件は、設計どおりに
  作ったかしか確かめず、指示を満たすかを確かめない
- テストで挙動を確かめられることだけを入れる。ドキュメントの追記は `dod` か `scope` に書く。受入条件に
  入れると、ドキュメントを文字列として読むテストになる。そのテストは書く前なら落ちるので、実装の前に
  落ちるかでは見分けられない

### 検証コマンド

- driver はコマンドを `bash -lc` でそのまま流す。パイプやリダイレクトを書いてよい
- タスクの `taskTests` には、そのタスクのテストを流すコマンドを入れる。空だと、テストが実装の前に落ちる
  ことを確かめられない
- ブリーフの「軽い検査」「回帰テスト」の分け方を、そのまま `quickChecks`・`regressionTests` に写す
- 回帰テストを `quickChecks` に移さない。`quickChecks` は実装タスクの完了チェックのたびに流れるので、
  遅い検査を入れると毎回待つことになる
- `quickChecks` にも、どのタスクを積んだ時点でも通るコマンドだけを入れる。完了チェックと積む前に毎回
  流すので、後のタスクで作るファイルを確かめるコマンドを入れると、前のタスクが積めなくなる。そういう
  コマンドはそのタスクの `taskTests` に入れる。`regressionTests` も同じく、積んだ時点で通るものだけを入れる
- ドキュメントの文言を grep するコマンドを入れない。言い換えや節の移動で落ち、挙動は何も確かめない

## 3. 設計ファイル

テストを書くステージは、設計ファイルにある形だけを呼んでテストを書く。書かなかった形はテストを書く
ステージが決めることになり、誰も確かめないまま実装を縛る。

書くもの:

- テストの入口になる関数・型・コマンドの置き場所（パス）・シグネチャ・引数と返り値の型・失敗の返し方
  （例外か値か、どの例外か）
- タスクの境界をまたぐ形と、どのタスクが作りどのタスクが使うか
- 2 つ以上の層をまたぐときだけ、データの流れ（Mermaid の図）

書かないもの: タスクの内部（private な関数・中間の型・内部の型の欄）、既存テストの追随、エッジケースや
順序の規約。書くと設計レビューがそこを詰めにきて、往復が終わらない。テストが内部の型を直に組み立てる
リポジトリでも、内部の型の欄は書かない（テストを書くステージが決めてよい）。

分量は変更の大きさに合わせる。関数を 1 つ直すだけなら「呼ぶ関数とシグネチャは今のまま
（`src/range.py:12` の `parse_range(text: str) -> Range`）」の数行で足りる。
