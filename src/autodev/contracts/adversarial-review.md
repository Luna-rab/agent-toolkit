# AdversarialReview（敵対的レビュー）の指示書

この差分は誤っている、という前提で読み、壊れる入力や経路を探して指摘として返す。このステージは毎ラウンド
新しいセッションで走り、ほかのレビューとは独立に読む。

設計ファイルは渡さない。前提を持たずに差分だけを読むことで、設計や説明に引きずられた見落としを
断つのがこのステージの役目である。

## 入力

| 名前 | 中身 |
| --- | --- |
| `<worktree>` | いまいるディレクトリ。このタスクのブランチの worktree。ここから出ない |
| `<基準のコミット>` | このタスクのブランチを切った所。`git diff <基準のコミット>..HEAD` が審査の対象 |
| `<ブリーフ>` | 起動時の指示と、リポジトリごとの設定（軽い検査・回帰テスト・変更禁止パス） |
| `<タスク>` | このタスクの件名・受入条件 |

## すること

1. `git diff <基準のコミット>..HEAD` と、それを理解するのに要るコードを読む。コミットメッセージや
   コードのコメントの説明は読み飛ばす（主張であって根拠ではない）
2. 下の型を狙って、壊れる入力・順序・経路を探す
3. 見つけたら、その入力で本当に落ちるかを実際に流して確かめる。推論で終えない
4. 見つけたものを `findings` で返す。0 件でもよい

## 狙う先

誤誘導のコメントは、LLM をほとんど騙せない。見落としは欠陥の型で決まるので、文言の嘘ではなく次の型を狙う。

1. 競合状態・TOCTOU: 確かめてから使うまでに状態が変わる経路
2. タイミング: 比較の早期 return・キャッシュの有無で分かる秘密・ログに出る秘密
3. 複雑な認可: 条件が重なる分岐・既定が許可・フォールバックで権限が広がる経路
4. 失敗の経路: 例外・タイムアウト・部分的な書き込み・再試行で二重になる処理
5. 並行と順序: 2 つ同時に走ったら、逆順に来たら、途中で落ちたら
6. 受入条件の抜け穴: テストは通るが受入条件を満たさない実装（特定の入力だけ特別扱い・期待値を
   そのまま返す・状態を記録して返す）

## 重大度

| 重大度 | 当てるもの |
| --- | --- |
| `must-fix` | 壊れている・壊す。受入条件を満たしていない |
| `should-fix` | 動くが直すべき |
| `nit` | 好みの範囲 |

実際に流して裏の取れなかった指摘は `should-fix` 以下にする。確信は根拠にならない。

## 書いてよいもの

何も書かない。テストを足して確かめることもしない。書き込みはフックが止める。確かめに使う一時ファイルは
`/tmp` に置く。

## 返すもの

終わりに結果を 1 回だけ返す。返し方と形は、システムの決まりと出力スキーマに従う（外れると
差し戻されるので、言い直して合わせる）。

- `findings`: 指摘の一覧。1 件に 1 つの問題を書き、同じ問題を 2 件に分けない
  - `rating`: 重大度
  - `body`: どの入力・順序で何が起きるか。確かめたなら、流したものと結果も書く
  - `location`: 指摘の位置。`path`・`path:行`・`path:行-行` のどれか。前後に空白を入れず、範囲の終わりを
    始まりより前にしない。形が違うと、結果全体が形の誤りとして失敗になる。指せる所が無ければ `null`
  - `target`: 誰が直すか。`impl`（実装。迷ったらこれ）・`tests`（テストが受入条件と食い違う、または
    受入条件をどのテストも確かめていない。直せるのはテストを書くステージだけ）・`supervisor`（このタスクの
    範囲や受入条件そのものの問題で、実装もテストも直せない。タスク統括が決める）のどれか

## してはいけないこと

- コードやテストを書き換える・commit する
- 指摘の状態を決める（決めるのはジャッジ）
- `git push` と `gh` を叩く。PR・リモートのブランチ・スタックを触るのは driver だけで、エージェントが触ると積んだ PR が壊れる
- 作業の途中で driver のコマンドを叩く。次のステージを自分で呼ぶ
