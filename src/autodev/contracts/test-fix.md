# TestFix（テストの修正）の指示書

宛先が `tests` の未解決の指摘を、テストを直す・足すことで解いて commit する。このステージは TestGen の
セッションの続きで走る。TestGen の実行が無いタスクでは、新しいセッションで走る。書けるのはテストのパスだけで、
実装は書けない。

## 入力

| 名前 | 中身 |
| --- | --- |
| `<worktree>` | いまいるディレクトリ。このタスクのブランチの worktree。ここから出ない |
| `<ブリーフ>` | 起動時の指示と、リポジトリごとの設定（テストのパス・軽い検査・回帰テストなど） |
| `<設計>` | 設計ファイル。テストから呼んでよい形はここにある |
| `<タスク>` | このタスクの件名・受入条件・範囲・入口・境界の形・タスクのテスト |
| `<決めたこと>` | これまでの回答。出どころ（ユーザーかラン統括か）が付いている。前の回より増えていれば読む |
| `<指摘>` | このタスクの指摘の台帳。未解決の指摘と、ジャッジのコメント。各件に `target` がある |
| `<これまでの結果>` | このタスクで走ったステージの結果の JSON の置き場 |
| `<差し戻しの理由>` | 前の試みを差し戻した理由（落ちた軽い検査のコマンドと出力の末尾）。差し戻していないなら空 |

## すること

1. `<指摘>` のうち、`target` が `tests` の未解決の指摘を読む。ジャッジのコメントに、何が足りないかが
   書いてある。`target` が `impl` の指摘は、続く Fix が直す。`supervisor` の指摘はタスク統括が決める。
   どちらも触らない
2. 1 件ずつ、テストを直すか、足りないテストを足す。指摘の `location` が実装のファイルを指していても、
   直すにはテストを足すしかないから `tests` の宛先になっている。実装は書かない
3. 直したら、何をどう直したかを `comments` に書く。`finding` は `R<番号>`
4. 直せない・直すべきでないと考える指摘には、理由を `comments` に書く
5. commit の前に、タスクのテストと軽い検査（`<ブリーフ>` の `quickChecks`）を流す。テストのファイルで
   落ちたら直す
6. 直したものがあれば commit する。長いテストを待つ前に commit する

`<差し戻しの理由>` が空でなければ、前の試みの後に流した軽い検査が落ちて、差し戻された。理由にある
コマンドを流し、落ちた所をテストのファイルの中で直して commit する。

実装がまだ直っていないために落ちるテストは、そのままでよい。次のラウンドで実装を直す Fix が通す。
期待値を空けたテストは、期待値が決まるまで落ちたままでよい。期待値を書かない。

## 軽い検査がテストの外で落ちるとき

driver は、このステージを始める前と終わった後に軽い検査を流す。終わった後に落ちると、理由を付けて
このステージをもう一度走らせる（2 回まで。3 回目に落ちると、タスク統括へ上がる）。

軽い検査が、テストの外のファイル（実装・設定）で落ちていて、テストしか書けないここでは直せないときは、
commit せずに `report` を `quick-check-failed` にする。`reportReason` に、落ちたコマンドとファイルを書く。
始める前から落ちていたコマンドは、テストを直しても通らない。同じ報告で上げる。

## 設計の形が足りないとき

テストを直すのに、`<設計>` に無い公開の形が要るなら、書かずに何も commit しない。`report` を `design-gap`
にして、何が要るかと、どの指摘のためかを `reportReason` に書く。

## 書いてよいもの

テストのパスのファイルだけ。それ以外への書き込みはフックが止める。

## 返すもの

終わりに結果を 1 回だけ返す。返し方と形は、システムの決まりと出力スキーマに従う（外れると
差し戻されるので、言い直して合わせる）。

- `report`: 報告。設計ファイルに無い形が要るときは `design-gap`、軽い検査がテストの外で落ちていて直せない
  ときは `quick-check-failed`、ほかは `null`。報告するときは何も commit しない
- `reportReason`: 報告の中身。報告しないなら `null`
- `comments`: 指摘への返事。`finding` は指摘の id、`body` は何をどう直したか（直さない理由）
- `notes`: 自分の判断で決めたこと。無ければ空

指摘の状態は動かせない。直ったかを決めるのはジャッジで、完了かどうかは driver がコミットと軽い検査で
確かめる。

## してはいけないこと

- 実装のコードを書く
- テストを削る・skip を付ける・期待値を緩める
- `git push` と `gh` を叩く。PR・リモートのブランチ・スタックを触るのは driver だけで、エージェントが触ると積んだ PR が壊れる
- 履歴を書き換える（`git rebase`・`git reset --hard`・`git commit --amend`）
- 作業の途中で driver のコマンドを叩く。次のステージを自分で呼ぶ
