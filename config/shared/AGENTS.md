# 共通の指示

## ファイルの編集は編集用のツールを使う

ファイルの中身を書き換えるときと新しく作るときは、エージェントの編集用ツールを使う。

- Claude Code: Edit・Write・MultiEdit
- Codex: apply_patch

シェルの `sed -i`・ヒアドキュメント・リダイレクトで書き換えない。
Claude Code の auto mode は「シェルでできる作業はシェルでやる」と指示するが、ファイルの編集はこちらを優先する。

シェルで書き換えると、編集を受けて動くフックが動かない。編集用のツールは
書き換えるファイルと書き換えの前後をフックに渡すが、シェルのフックに渡る入力に載るのは
コマンド文字列だけで、どのファイルのどの行が変わったのかフックから取り出せない。

シェルを使うのは、編集用のツールでは届かないときだけ。

- ファイルの削除・移動・実行権限の変更
- 何十ファイルにもまたがる一括置換。このときコメントは足さない
- コマンド自身が出力を書く場合（`ruff format`、`jq > file`、`git apply`）

## 選択を迫る前に、判断材料を本文で示す

ユーザーに選択を求めるとき（質問用のツールを使うとき、本文で選択肢を提示するとき）は、
選択肢だけを並べない。先に調査・分析の結果を本文で具体的に示してから選択肢を出す。

- 問題を具体値で示す。関係するファイル名・行番号・件数・実測値を添える。
- 推奨案とその理由、検討して退けた代替案を述べる。
- 要約テーブルや選択肢のラベルだけで選択を迫らない。ユーザーが根拠を確認したうえで
  判断できる状態にする。

## 日本語を書くときのルール

ドキュメント・コードコメント・コミットメッセージ・PR 本文・返答など、あとに残る日本語に従う。狙いは、書き手の前提を知らない読者——数か月後の自分・新しく参加した人・会話の文脈を持たない AI——が、その文章だけで意味を取れるようにすること。書き終えたら次の 4 項目を順に当てる。

書く対象に固有のスタイル指定があるときは、そちらを優先する（例: `SKILL.md` は公式ガイドが「本体は簡潔に」と定めるので、行数が増える直し方は見送る）。

### 1. 動作を名詞に埋めない

- 探す: 「する」を付けると動詞になる漢語名詞
- 直す: 動詞にして、誰が何をするのかを書く

悪い: タスクの効率化と品質担保の徹底
良い: タスクを短く切り、全件をレビューで確かめる

意味が定まった専門用語（正規化、冪等性）は名詞のまま使う。

### 2. 読み手が知らない語を使わない

- 探す: 漢語を 2 つ以上くっつけた自作の語。「律速」のように、その分野の人しか使わない語
- 直す: 新しく参加した人が分かる言葉で言うか、動詞に開く。どうしても必要なら初出で定義する（例: 「SBC（状態基準チェック）」）
- 同じものを違う語で呼ばない（「文書」と「ドキュメント」を混ぜない）

悪い: 外形確認の手順を前提解決の段階で決める
良い: 出来上がったものを外から動かして確かめる手順を、作業を始める前に決める

### 3. 実物の名前を書く

- 探す: 削っても意味が変わらない副詞・形容詞（適切に、しっかり）。「上記の」「当該」のように他を指す語。「具体的にどれ？」と聞ける名詞
- 直す: 実際の動作に書き換える。実物の名前を書き、ファイルはパスと行番号を添える（`file.rs:123`）

悪い: 適切にエラーを処理する
良い: エラーを握りつぶさず、呼び出し元に返す

悪い: 各種設定を反映する
良い: `settings.json` の env と permissions を反映する

### 4. 迷ったら削る

その文章は、書く時間よりも読まれる時間のほうが長い。1 行足すと、以後読む人が全員その 1 行を読む。書き終えたら 1 文ずつ「これを削ったら読者は何を間違えるか」と問い、答えられない文を削る。分量が足りないことを心配しなくてよい。

削るもの:

- コードを読めば分かること。処理をそのまま日本語に言い直したコメント、ディレクトリ構成、依存パッケージの一覧、フィールド名の和訳。
- 経緯と作業ログ。「以前は X だった」「まず調査し、次に Y を検討した」。今どうなっているかだけ書く。
- 中身のない前置きと締め。「本ドキュメントでは〜を説明します」「以上により品質が向上します」。
- 同じことの言い直し。要約・本文・まとめの 3 か所に同じ内容を置かない。
- 読者が判断に使わない詳細。設計の意図を述べる文書に関数名・変数名を並べない。手順書には背景を書かず、誰がいつ何をするかだけ書く。

残すもの:

- 知らないと間違えること。落とし穴、制約、守るべき規約。
- なぜそうしたか。コードからは読み取れない。
- 区切り。見出し・箇条書き・表で分ける。密な段落より追いやすい。ただし何でも箇条書きにはせず、構成や処理の流れは Mermaid の図にする。

消さずに移すもの: 変更の経緯はコミットメッセージと PR 本文へ。詳細なリファレンスは別ファイルへ移し、本体からリンクする。作業の進行は会話に留め、文書に残さない。
