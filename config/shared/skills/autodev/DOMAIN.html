autodev のドメイン

このページは、autodev が何を決め、どんな規則で状態を変えるかを、DDD（ドメイン駆動設計）の用語で説明する。ドメインのコードは src/autodev/domain/ にある。autodev の使い方は README.md に書いてある。

1. autodev が解く問題

autodev は、ユーザーから指示を 1 つ受け取り、計画、テスト、実装、レビューを経て、GitHub に stacked PR を作るところまでを、人が見ていなくても進める。stacked PR とは、ある PR のブランチを base にして次の PR を作り、PR を下から順に重ねたものである。autodev は PR をマージしない。ユーザーが、autodev の作った PR をレビューし、一番下の PR から順にマージする。

autodev は次の部品で動く。ランとタスクは 2 章で定義する。

  • driver は Python のプロセスで、イベントを記録し、ステージと統括を起動する。イベントは、状態が変わったことを表す記録である（4 章）
  • ステージは、タスクの中の 1 つの手順である。ステージは、LLM を 1 回呼び出す（claude -p を 1 回実行する）か、LLM を使わない決まった処理（git を操作する処理や、検証コマンドを動かす処理など）を 1 回実行する
  • 統括（Supervisor）は、ドメインの規則では決められないことを判断する LLM またはプログラムである。ラン統括はラン全体を、タスク統括はタスク 1 つを受け持つ
  • ドメインは、autodev の状態と、状態を変えるときに守る規則をまとめたコードである

人が見ていない間も PR の作成を進めるために、ドメインは次の 3 つを規則で決める。

  • 次にどのステージを実行するか。また、ステージの結果を合格とするかどうか
  • ステージや統括が解決できない問題に当たったとき、誰に判断を尋ねるか。問題の例は、ステージが 2 回続けて失敗したことや、ステージが設計の穴を報告したことである。autodev は、問題を受け手に送って判断を求めることをエスカレーションと呼ぶ。受け手は、タスク統括、ラン統括、/autodev、ユーザーである（6 章）
  • 同じ修正や再計画を繰り返すとき、何回目で止めるか。ドメインは、修正の回数、設計のラウンドの数、再計画の回数に上限を設けている
担い手決めること決めないこと
ユーザーユーザーは質問に答える。また、autodev が作った PR をレビューしてマージする。ユーザーは、次にどのステージを実行するかなどの進め方を決めない。
/autodev/autodev スキルは driver を起動する。driver が出した質問をユーザーに渡し、ユーザーの回答を driver に届ける。/autodev は質問に自分で答えない。ステージで何をするかも決めない。
driverdriver はイベントを記録する。また、ドメインが返したステージと統括を起動する。driver は、進め方とステージの合否を自分では決めない。driver はドメインの関数を呼び、その結果に従う。
ドメインドメインは、次に実行するステージ、ステージの合否、状態の遷移、エスカレーションの受け手を決める。規則で決められない判断は、統括が下す。ドメインの wake_for が起動する統括を返し、driver がその統括を起動して判断を求める。
統括統括は、フローの組み方と、再計画するかどうかと、エスカレーションにどう答えるかを決める。統括は、規則に反することを決められない。統括の判断が規則に反する場合、集約はその判断を受け付けない。driver が、受け付けなかった理由を添えて、統括に判断を返し直させる。
ステージステージは、タスクの中の 1 つの手順を行う。例: 設計を書く、テストを書く、レビューする、push する。ステージは次に何をするかを決めない。

2. ユビキタス言語

ユビキタス言語とは、開発者が話すときも、コードやログを書くときも、同じ意味で使う用語の集まりである。autodev のユビキタス言語は、次の表の用語である。autodev のコードとログも、この表の用語を使う。表の括弧の中は、コードでの名前である。

用語意味
ラン（Run）ランは、1 つの指示について、autodev が計画からすべての PR のスタックへの追加までを進める、1 回分のまとまりである。ランは名前を持つ。autodev は、ランの記録を既定で ~/.local/state/autodev/<ラン名>/ に保存する。環境変数 AUTODEV_STATE_DIR か XDG_STATE_HOME を設定すると、保存場所が変わる。
タスク（Task）タスクは、ランを分けた単位である。タスクは、それぞれがフロー（ステージの並び）を持つ。タスクには次の 3 種類がある。
計画タスク（planning）計画タスクのステージは、受入条件と設計と実装タスクの一覧を書く。1 つのランには計画タスクが 1 つある。
実装タスク（task<番号>）実装タスクは、PR 1 本分の変更を作る。running の実装タスクと escalated（回答待ち）の実装タスクの数は、合わせて既定で 3 つまでである。
git 管理タスク（git）git 管理タスクは、GitJob を 1 つずつ処理する。GitJob の例は、ブランチの作成、スタックへの PR の追加、概要 PR の作成である。1 つのランには git 管理タスクが 1 つある。
ステージ（Stage）ステージは、タスクの中の 1 つの手順である（1 章）。ステージの例は Plan、TestGen、Impl、Review、Gate、Push である。
フロー（Flow）フローは、タスク統括が組むステージの並びである。cursor は、フローの中で、Task が次に実行するステージの位置を指す値である。ドメインの FlowValidator は、フローを実行する前に検査する。Task は、規則に合わないフローを受け付けない。
実行（Execution）実行は、Task がステージを 1 回起動するごとに作る記録である。ステージが失敗してやり直すときは、Task は新しい実行を作る。
成果物（Artifact）成果物は、ステージが作り、後のステージが使うものである。成果物の例は、設計（design）、テスト（tests）、実装（impl）、レビュー済みであること（reviewed）、完了チェックに合格したこと（gated）、PR 本文（pr-body）である。
指摘（Finding）指摘は、レビューで見つかった問題 1 件である。指摘は重み（must-fix、should-fix、nit）と状態を持つ。指摘の id は、レビューの指摘なら R<番号>、完了チェックの指摘なら G-<項目>、設計の指摘なら D<番号> である。
ReviewLedgerReviewLedger は、1 つのタスクまたは設計について、すべての指摘を記録する集約である（4 章）。
ジャッジ（Judge・DesignJudge）ジャッジは、指摘ごとに、指摘が直ったか（closed）と、指摘が妥当でないか（rejected）を判定するステージである。ReviewLedger は、その指摘を判定すると決まっているステージの結果を受け取ったときに限り、指摘の状態を変える（4 章）。
合成ステージ・ラウンド合成ステージは、複数のステージを組み合わせたステージで、ReviewLoop と DesignLoop の 2 つがある。合成ステージの 1 ラウンドでは、まずレビューするステージ（Review や DesignReview）を並列に実行し、次にジャッジが指摘を判定し、最後に修正するステージ（Fix・TestFix や Revise）を実行する。ReviewLoop の指摘は宛先（supervisor・tests・impl）を持ち、ジャッジの判定の後、宛先で行き先が決まる。supervisor があればタスク統括へ supervisor-finding で上げて回答を待ち、tests があれば TestFix（テストだけを書く）、impl があれば Fix を、この順に同じラウンドで実行する。指摘が残っている間、Task は次のラウンドを始める。
統括（Supervisor）統括は、規則で決められないことを判断する。統括には 2 種類ある。ラン統括は LLM で、1 つのランに 1 つある。タスク統括はタスクごとに 1 つある。実装タスクのタスク統括は LLM である。計画タスクと git 管理タスクのタスク統括は、決まった並びのフローを組むプログラムである。
モデルのクラス（ModelClass）モデルのクラスは、LLM のステージと統括が claude に渡すモデルと effort を決める区分で、役割ごとに lead、review、implement、write の 4 つがある。レビューを別のクラスに分けているので、レビューにだけ別のモデルを当てられる。どのステージと統括がどのクラスかはドメインが固定する（lead はラン統括・タスク統括と Plan・Replan・Revise・DesignJudge・Judge、review は DesignReview・Review・AdversarialReview、implement は TestGen・TestFix・Impl・Fix・Expect・ResolveConflict、write は WritePrBody・WriteOverview）。ジャッジはレビューの指摘を裁くので、review ではなく lead に置く。クラスごとのモデルと effort の既定は lead が opus/high、review が opus/medium、implement と write が sonnet/medium で、利用者は ~/.config/autodev/models.json で変えられる。autodev は新しいランを始めるときに 1 回だけ設定を読み、RunStarted に記録する。呼び直したランは記録した値を使い続ける。
エスカレーションエスカレーションは、ステージや統括が解決できない問題を、受け手に送って判断を求めることである。受け手は、タスク統括、ラン統括、/autodev、ユーザーの順に並ぶ（6 章）。ステージで起きた問題は Task が送る。エスカレーションは種類（EscalationKind）を持つ。種類の例は、stall（指摘の停滞）、supervisor-finding（宛先が supervisor の指摘）、design-gap（設計の穴）、gate-unfixable（完了チェックで、コードを直しても解決しない不合格）である。
停滞（Stall）停滞は、その指摘の宛先の修正するステージ（宛先が impl なら Fix、tests なら TestFix）が 2 回完了した後も open のまま残っている指摘を指す。Task は、停滞した指摘を stall という種類のエスカレーションとして送る。
完了チェック（Gate）完了チェックは、実装タスクをスタックに追加する前に行う検査である。検査する項目の例は、コミットがあること、open の指摘が無いこと、テストを書き換えていないこと、タスクのテストと軽い検査が成功することである。
検証コマンドの種類検証コマンドは 3 種類に分かれ、種類ごとに流す時点が違う。タスクのテスト（taskTests）はそのタスクのテストで、ConfirmRed と Gate が流す。軽い検査（quickChecks）は lint や型検査のように速く、どのタスクを積んだ時点でも通るもので、TestGen の前後・ConfirmRed・Gate・統合検査が流す。TestGen を差し戻すかどうかは、終わった後に落ちたコマンドが始める前（baseline）から落ちていたかで決まる。回帰テスト（regressionTests）はテスト全体のように遅く、ほかの場所を壊していないかを確かめるもので、統合検査だけが流す。
統合検査（IntegrationCheck）統合検査は、タスクをスタックに積む前に、スタックの一番上で軽い検査と回帰テストを流すステージである。
提案・設計・設計の改訂番号提案は、計画のステージ（Plan、Replan、Revise）が返す、確定する前の設計の案である。DesignLoop で Design 集約が提案を確定すると、その提案は設計になる。設計の本文は design/v<改訂番号>.md に保存する。改訂番号（DesignVersion）は設計ファイルの番号で、新しい設計ファイルは前のファイルより大きい改訂番号を持つ。古い改訂番号のファイルは削除しない。
計画の反映・再計画計画の反映は、確定した設計にあるタスクの一覧を Run に登録することである。再計画は、ランの途中で計画を書き直すことである。再計画のステージ（Replan）は、止めるタスクと破棄するタスクも提案する。
スタック（Stack）スタックは、下から順に重ねた PR の列である。一番下の PR は概要 PR である。git 管理タスクは、新しい PR を必ず一番上に追加する。
概要 PR概要 PR は、ランのまとめと判断の記録を載せる PR である。概要 PR の base は、ランの base ブランチである。git 管理タスクは、概要 PR を draft で作る。ランが終わったときに、ラン統括が draft を外すと決めた場合に限り、仕上げの GitJob が概要 PR の draft を解除する。
GitJobGitJob は、git 管理タスクが行う git と GitHub の操作 1 つを表す。GitJob の種類には、ブランチの作成、概要 PR の作成、スタックへの追加、破棄、仕上げなどがある。仕上げは、ランが終わったときに概要 PR のまとめを書き、ラン統括が決めた場合は概要 PR の draft を解除する GitJob である。すべての GitJob は 1 つのキューに並ぶ。
破棄・追加し直し破棄は、スタックに追加済みのタスクを、再計画によってスタックから外すことである。破棄したタスクより上にあったタスクは、git 管理タスクが新しいブランチ名でスタックに追加し直す。
統合の失敗・引き継ぎ統合の失敗は、git 管理タスクがタスクのブランチを rebase したときに衝突が起き、両方のブランチの変更を残す形で衝突を解決できなかったことを指す。統合に失敗すると、git 管理タスクは integration-failed という種類のエスカレーションを送る。引き継ぎは、ラン統括が新しいタスクを差し込み、その新しいタスクが ResolveConflict のステージで衝突を解決し直すことを指す。統合に失敗した元のタスクの状態は superseded になる。
質問・回答質問は、ラン統括が /autodev を通してユーザーに尋ねることである。ラン統括は、1 つのエスカレーションをもとに質問を出す。ユーザーの回答は Run が記録し、ラン統括がその回答を添えてエスカレーションに答える。Run は、1 つの回答を 2 回使うコマンドと、質問のもとになったエスカレーション以外に回答を使うコマンドを受け付けない。
ランの段階（RunPhase）RunPhase は、ランが今どの段階にあるかを表す。値は not-started、planning、running、panicked、finishing、finished の 6 つである。status --json は RunPhase を出力する。
パニックパニックは、Claude の利用枠の上限に達したか、driver が停止のシグナル（SIGTERM、SIGINT）を受け取ったことを指す。パニックの後は、driver をもう一度起動するまで、autodev は新しいタスクを始めない。

3. 層とコンテキスト

autodev のコードは、app、infra、adapters、domain の 4 つの層に分かれている。外側の層は domain を import するが、domain は外側の層を import しない。また、domain は I/O（ファイル、プロセス、ネットワークの読み書き）を行わない。test/autodev/test_layers.py は、domain がこの 2 つの決まりを守っているかをテストする。

開発者は、ビジネスロジック（何をしてよいか、次に何をするかを決める規則）を domain の層にだけ書く。ほかの層のコードは、判断が必要な場面でドメインの関数を呼び、返った結果のとおりに処理を実行する。

  • app のメインループは、ポリシーと反応を、イベントを受け取る関数として登録する。メインループは、driver が記録したイベントをそれらの関数に配る。どのイベントからどのコマンドを作るかは、ドメインのポリシーが決める
  • 反応（reaction）は、イベントの中身に従って I/O を実行する app の関数である。I/O には、ファイルの書き込み、ステージの起動、統括の起動がある。反応を実行するかどうかと、何を実行するかは、ドメインがイベントを返した時点で決めている。たとえば、統括を起動するかは wake_for が決め、ask で止まったステージの続きは policies/registry.py の FOLLOW_UPS が決める
  • ステージの実行器（app の層にある）は、ステージを起動し、終わるまで待つコードである。実行器は、証拠（ステージの終了の仕方、HEAD、ステージが作ったファイル、検証の結果）を集めて Task に渡す。Task が、その証拠をもとに、ステージの結果を完了、失敗、エスカレーションのどれにするかを決める
  • adapters は、外部の仕組み（claude -p、git、gh）から得た事実を返す。adapters は、処理を許すか止めるかを決めない。たとえば、ガードのフック（adapters の層にある）は、LLM のステージがファイルを書き込もうとするたびや、コマンドを動かそうとするたびに、Claude Code が呼び出す PreToolUse フックである。ガードのフックは、書き込むファイルのパスがどの場所（WriteZone）に当たるかを調べ、その結果をドメインのガードの規則に渡す。書き込んでよいかどうかは、ガードの規則が決める

4. 集約

集約
集約は、関係するデータと、そのデータを変えるときに守る規則をまとめた単位である。集約の外のコードが集約の状態を変えるときは、必ず集約にコマンドを送る
コマンド
コマンドは、集約に「この操作をしてほしい」と依頼するメッセージである。集約は、handle というメソッドでコマンドを検査し、イベントを返す。コマンドが規則に合わない場合、集約はそのコマンドを受け付けない
イベント
イベント（ドメインイベント）は、集約がコマンドを処理した結果を表す「起きたこと」である。集約の handle がイベントを返し、イベントストアがそのイベントを events.db に追記する。イベントの名前は過去形にする（例: TaskStarted）。追記したイベントは書き換えない
ポリシー
ポリシーは、ある集約のイベントを受け取り、別の集約へ送るコマンドを返す規則である

autodev には集約が 6 つある。それぞれの集約は、自分のストリームを持つ。ストリームは、1 つの集約のイベントを、イベントストアが追記した順に並べた列である。集約は、ほかの集約の状態を読まない。集約どうしは、イベントとポリシーを通してつながる（5 章）。

Run — ランの全体

Run は、タスクどうしの依存関係のグラフと、各タスクの状態を持つ。Run は、どのタスクをいつ始め、いつ止めるかを決める。ラン統括が下した判断は、質問を除いて、すべて Run がコマンドとして受け取る。最初の計画を Run に反映するコマンド（ApplyPlan）は、ポリシーが送る。ラン統括が apply-plan という判断を返すと、driver はその判断を、再計画を反映するコマンド（ApplyReplan）にして Run に送る。

Run は次の規則を守る。

  • Run が実装タスクを始めるのは、次の 3 つの条件がすべて成り立つときに限る。1 つ目は、そのタスクがまだ始まっていない（pending）こと。2 つ目は、そのタスクが依存するタスクが、すべてスタックに追加済みであること。3 つ目は、running の実装タスクと escalated の実装タスクの数の合計が、並列の上限より少ないこと
  • 依存関係のグラフに循環があってはならない。また、あるタスクが依存するタスクは、止めたタスクや破棄したタスクであってはならない。Run はタスクの番号を再利用しない
  • Run は、スタックに追加済みのタスクを止めるコマンドを受け付けない。Run が追加済みのタスクをスタックから外すのは、確定した再計画がそのタスクの破棄を提案した場合に限る
  • 次のどれかに当てはまる間、Run はランを終えるコマンド（FinishRun）を受け付けない
    • 終端の状態にない実装タスクが残っている
    • 計画タスクが計画または再計画を進めている
    • 破棄したタスクから上の PR を閉じ終えていないか、その上にあったタスクを gated に戻し終えていない
  • Run は、タスクを 1 つもスタックに追加しないまま行う再計画を、2 回まで受け付ける。3 回目の再計画を受け付けるには、ユーザーの回答が必要である
主に受け取るコマンド
StartRun・ApplyPlan・ApplyReplan・RequestReplan・InsertTask・StopTasks・EscalateToRun・AnswerEscalation・FinishRun
主に返すイベント
RunStarted・TaskStarted・TasksPlanned・ReplanRequested・TaskInserted・TasksStopped・TasksDiscarded・TaskStatusChanged・TaskMarkedStacked・AllTasksSettled・RunFinished

Task — タスク 1 つの中身

計画タスク、実装タスク、git 管理タスクの 3 種類とも、同じ Task 集約で表す。Task はフローと cursor を持つ。Task は、次に実行するステージを決める。また Task は、実行器が集めた証拠をもとに、ステージの結果を完了、失敗、エスカレーションのどれにするかを決める。

ask は、計画のステージ（Plan、Replan、Revise）の LLM が、ユーザーに質問するために実行するコマンド（autodev ask --question <質問>）である。ガードのフックは、回答がまだ無い ask のコマンドを保留する。その結果、ステージの実行は deferred の状態で止まる。回答が届くと、実行器がそのセッションを続きから再開し、ask は回答を LLM に返す。

Task は次の規則を守る。

  • 次のどれかに当てはまる間、Task は次に実行するステージを決めない。ただし、状態が requested の実行は、この場合も実行器が起動する
    • 回答を待っているエスカレーションがある
    • Task がフローを破棄し、新しいフローをまだ受け付けていない
    • 完了チェックで不合格になった項目について、ReviewLedger の判定を待っている
  • ステージの中には、結果をほかの集約へ渡すものがある。渡す結果は、指摘、判定、提案、作った概要 PR、スタックに追加した PR、破棄で閉じた PR の範囲である。このようなステージが完了しても、結果を受け取った集約が ResultReceived を返すまで、Task は cursor を進めない。受け取った集約が ResultRefused を返した場合、Task は result-refused という種類のエスカレーションを送る
  • フローの同じ位置のステージが 2 回続けて失敗した場合、Task は stage-errors という種類のエスカレーションを送る。1 回目の失敗では、Task はそのステージをやり直す
  • TestGen と TestFix は、始める前（同じ位置の最初の試みだけ）と終わった後に、driver が軽い検査を流す。終わった後に落ちたコマンドが始める前（baseline）から落ちていたなら、Task は差し戻さず quick-check-failed で上げる。このステージで落ちたなら、Task は StageSentBack を出し、統括を通さずに同じ位置を新しい実行でやり直す。差し戻した後の試みも、最初の試みの baseline と比べる。差し戻しは 2 回までで、3 回目に落ちたら quick-check-failed で上げる。TestFix の最初の試みの baseline は、ReviewLoop のラウンドごとに取り直す。数えるのはそのフローの間だけで、フローを書き直すか、同じ位置が完了すると 1 から数え直す。TestGen・TestFix が quick-check-failed か design-gap を報告したときは、軽い検査の結果を見ずにその報告で上げる
  • 回答を待っているエスカレーションがある間、Task が受け付けるフローは、そのエスカレーションに対応するフローに限る
  • 実装タスクのフローには、Gate と WritePrBody を必ず含める。どちらかが欠けたフローを、Task は受け付けない
主に受け取るコマンド
OpenTask・AcceptFlow・BeginStage・ReportStageResult・ConfirmHandoff・ConcludeReviewRound・ResolveEscalation・StopTask
主に返すイベント
FlowAccepted・StageRequested・StageStarted・StageCompleted・StageFailed・EscalationRaised・FlowFinished・TaskGated

ReviewLedger — 指摘の記録

ReviewLedger には 2 種類ある。タスクごとの ReviewLedger のストリームは review/<TaskId> で、設計の ReviewLedger のストリームは review/design である。

ReviewLedger は次の規則を守る。

  • 指摘の種類ごとに、その指摘を判定するステージが決まっている。レビューの指摘は Judge が、完了チェックの指摘は Gate が、設計の指摘は DesignJudge が判定する。ReviewLedger が指摘の状態を変えるのは、その ReviewLedger を持つタスクの中で実行器が実行した、判定するステージの結果を受け取ったときに限る
  • ReviewLedger は、指摘の状態を変えるとき、必ずコメントを一緒に記録する
  • タスクの ReviewLedger は、修正するステージ（Fix・TestFix）が完了するたびに、open で宛先がそのステージと同じ指摘（Fix は impl、TestFix は tests）の修正の回数を数える。判定のラウンドを終えるときに、タスクの ReviewLedger は、停滞した指摘があるかを調べる。設計の ReviewLedger は修正の回数を数えない。設計の修正の繰り返しは、Design 集約がラウンドの数を数え、上限で止める
  • 再計画で別のタスクへ移した指摘（carried）は、指摘を受け取るタスクの ReviewLedger に 1 回だけ登録する
主に受け取るコマンド
RecordFindings・RecordJudgement・RecordGateResult・CountFix・CarryFinding
主に返すイベント
FindingRaised・FindingClosed・FindingRejected・FindingReopened・FindingStalled・FindingsEvaluated・ResultReceived・ResultRefused

Design — 設計の改訂番号と、確定前の提案

Design は、計画のステージ（Plan、Replan、Revise）が返した提案を受け取る。DesignLoop の各ラウンドで、Design はラウンドの数を数え、DesignJudge の判定をもとに、提案を確定するか、修正に回すか、回答を待つかを決める。Design は、ステージの起動もファイルの書き込みも行わない。

Design は次の規則を守る。

  • Design が提案を確定するのは、DesignJudge が今の提案の改訂番号の設計を判定し、open の must-fix の指摘が 0 件の状態でラウンドを終えたときに限る。Design が提案を確定すると、must-fix 以外の open の指摘について、反応がその指摘を設計ファイルの末尾に書き足し、ポリシーがその指摘を rejected にする
  • Design は、これまでの改訂番号の一覧を持ち、古い改訂番号を一覧から消さない。新しい改訂番号は、前の改訂番号より大きい
  • Design は、1 つの提案について、DesignLoop のラウンドを 5 回まで数える。上限に達すると、Design は回答を待つ状態に移る
  • 回答を待っている間、Design は提案を修正に回さず、確定もしない
主に受け取るコマンド
ProposeDesign・ReviseDesign・SettleDesign・MarkReverted・MarkAmbiguous・ResumeDesign・DiscardProposal
主に返すイベント
DesignProposed・DesignRevisionStarted・DesignRevised・DesignSettled・DesignRoundsExhausted・DesignReverted・DesignAmbiguous・DesignProposalAbandoned

Stack — スタックの形と、GitJob のキュー

すべての GitJob は、種類にかかわらず 1 つのキューに並ぶ。git 管理タスクは、キューから GitJob を 1 つずつ取り出して処理する。Stack は、スタックの今の形を見て、GitJob を取り出してよいかと、GitJob の対象（PR を重ねる位置や、閉じる PR の範囲）を決める。そのため、キューは Stack 集約が持つ。

Stack は次の規則を守る。

  • スタックの一番下は概要 PR である。新しい PR は一番上にだけ重ねる。各 PR の base は、すぐ下の PR のブランチである
  • 処理中の GitJob は、同時に 1 つまでである。概要 PR ができるまで、Stack は、概要ブランチを作る GitJob と概要 PR を作る GitJob 以外を取り出さない。再計画が進んでいる間、Stack はスタックに追加する GitJob を取り出さない。タスクを破棄した後は、PR を閉じ終えるまで、Stack は一番上に PR を重ねる GitJob を取り出さない
  • GitJob の中には、終えないとランを終えられないものがある。git 管理タスクがそのような GitJob のフローを破棄した場合、Stack はその GitJob をキューの先頭へ戻す。Stack が戻すのは 2 回までである。2 回を超えると、Stack は GitJob を戻さずに止め、ラン統括が続けるかやめるかを決める
  • Stack は、一度スタックに追加したブランチ名と PR 番号の再利用を受け付けない。git 管理タスクは、スタックに追加し直すタスクのために、新しい名前のブランチを作り直す
主に受け取るコマンド
EnqueueGitJob・EnqueueStack・TakeNextGitJob・AppendEntry・RejectRequest・UnstackFrom・FinishGitJob
主に返すイベント
GitJobQueued・GitJobTaken・TaskStacked・IntegrationFailed・StackCutBack・GitJobFinished

Questions — ユーザーへの質問

Questions は、ラン統括が /autodev へ送った質問と、その回答を持つ。

Questions は次の規則を守る。

  • Questions は、同じ質問の id を 2 回使わない
  • 1 つのエスカレーションについて、回答を待っている質問は常に 1 つ以下である
  • Questions は、open の質問への回答だけを受け付ける。質問のもとになったエスカレーションが回答以外の理由で閉じた場合、Questions はその質問を取り下げる
主に受け取るコマンド
PostQuestion・AnswerQuestion・WithdrawQuestions
主に返すイベント
QuestionPosted・QuestionAnswered・QuestionWithdrawn

5. ドメインイベントとポリシー

集約は、ほかの集約を直接呼び出さない。ある集約が返したイベントをイベントストアが追記すると、ポリシーがそのイベントを受け取り、別の集約へ送るコマンドに変換する。ポリシーの一覧は policies/registry.py の表にあり、表は 80 行ある。表の 1 行は、「このイベントを受け取ったら、このコマンドを送る」という対応を 1 つ表す。

  • ポリシーは、受け取ったイベントとそのイベントの id だけを使ってコマンドを作る。ポリシーは集約の状態を読まない。状態によって決まること（取り出せる GitJob があるか など）は、コマンドを受け取った集約が決める。たとえば、取り出せる GitJob が無い場合、Stack は何もしない
  • ポリシーが送るコマンドの id は、受け取ったイベントの id とポリシーの名前から決まる。集約は、処理したコマンドの id を保持し、同じ id のコマンドを 2 回受け取ると、2 回目には何もしない。そのため、driver がイベントを配り直して、ポリシーが同じコマンドをもう一度送っても、状態は 2 回変わらない
  • ステージの結果をほかの集約へ渡すと、結果を受け取った集約は ResultReceived か ResultRefused を返す。ポリシーがそのイベントを受け取って Task にコマンドを送る。Task は、ResultReceived を受け取った場合は cursor を進め、ResultRefused を受け取った場合は result-refused という種類のエスカレーションを送る

6. エスカレーション

ステージで起きた問題は、Task がエスカレーションとしてタスク統括へ送る。エスカレーションの受け手は、下から順に、タスク統括、ラン統括、/autodev、ユーザーである。EscalationRouter（7 章）は、エスカレーションの受け手を、送った者のすぐ上の受け手に決める。そのため、エスカレーションが途中の受け手を飛ばすことはない。

回答は、エスカレーションを送った Task へ直接届く。具体的には、Run が回答を受け付けて EscalationAnswered を返し、ポリシーがエスカレーションを送った Task に ResolveEscalation を送る。タスク統括は回答を受け取らない。回答を受け取った Task は、止めていたフローを続ける。実行が ask で止まっていた場合は、実行器がその実行を続きから再開する。

notes は、Task が持つ回答の一覧である。Task は、受け取った回答を、回答した者（ユーザーかラン統括か）と一緒に notes に加える。実行器は、その後に起動するすべてのステージに notes を渡す。

  • Task は、次の 4 つの場合にエスカレーションを送る。1 つ目は、ステージが報告を返した場合である（報告の例は、設計の穴やテストの矛盾）。2 つ目は、フローの同じ位置のステージが 2 回続けて失敗した場合である。3 つ目は、指摘が停滞した場合である。4 つ目は、完了チェックで、コードを直しても解決しない不合格の項目が出た場合である。Task が送ってよいエスカレーションの種類は、タスクの種類ごとに決まっている
  • タスク統括がエスカレーションを受け取った場合、実装タスクのタスク統括（LLM）は、新しいフローを返してエスカレーションに対応するか、needs-replan または needs-human という種類のエスカレーションをラン統括へ送る。計画タスクと git 管理タスクのタスク統括はプログラムで、受け取ったエスカレーションを、種類を変えずにラン統括へ送る
  • ラン統括がエスカレーションを受け取った場合、ラン統括は、自分で回答する、再計画する、タスクを差し込む、タスクを止める、のどれかで対応する。または、ラン統括はユーザーに質問する
  • 統括が判断を返さない場合、driver は、次の 2 つの方法で、統括に判断を求め直す。どちらも app の SupervisorRunner が行う
    • 差し戻し: driver が統括の判断の JSON を解釈できない場合や、集約が判断を受け付けなかった場合、driver は理由を添えて、同じセッションに判断を返し直させる。差し戻しは 3 回までである
    • 呼び直し: 統括のセッションが判断を返さずに終わった場合、driver は同じセッションを続きから起動し直す。同じセッションでの起動は合わせて 2 回までである。それでも判断が返らない場合、driver は新しいセッションで 1 回だけ起動する
    差し戻しと呼び直しを上限の回数まで行っても統括が判断を返さない場合、driver はそのことを Run に伝える。タスク統括の場合は、ラン統括が supervisor-failed という種類のエスカレーションを受け取る。ラン統括の場合は、タスク統括のときと違い、1 回目からユーザーが受け取る。上の受け手が回答すると、反応は、判断を返さなかった統括を新しいセッションで起動し直し、前回の起動のきっかけになったイベントをもう一度渡す。同じイベントをきっかけに起動したタスク統括が、2 回を超えて続けて判断を返さなかった場合、Run は、ユーザーの回答を添えていないラン統括の回答を受け付けない
  • エスカレーションが回答以外の理由で閉じた場合、Task は、エスカレーションを送ったときに実行していたフローを破棄する。その後、統括が組んだ新しいフローを受け付けるまで、Task は次に実行するステージを決めない。エスカレーションが回答以外の理由で閉じるのは、たとえば Run がタスクを止めたときや、Run が再計画を反映したときである。Questions は、そのエスカレーションのために出した質問を取り下げる

7. ドメインサービス

ドメインサービスは、どの集約の状態にも属さない規則で判断する、ドメインの関数やクラスである。集約は、handle の中でドメインサービスを呼び出す。ドメインの外の層のコードも、判断が必要な場面ではドメインサービスを呼び出し、返った結果のとおりに処理を実行する。

サービス決めること
TaskSchedulerTaskScheduler は、実装タスクを今始めてよいかを決める。TaskScheduler は、始められるタスクを番号の小さい順に選ぶ。選ぶ数は、並列の上限から、running と escalated の実装タスクの数を引いた数である。
EscalationRouterEscalationRouter は、エスカレーションの受け手と、各受け手がさらに上へ送ってよいエスカレーションの種類を決める。
GateEvaluatorGateEvaluator は、完了チェックの項目ごとに合否を決める。GateEvaluator は、コードを直せば解決する不合格を G- の指摘にし、コードを直しても解決しない不合格をエスカレーションにする。
StallPolicyStallPolicy は、指摘が停滞したか（修正するステージが 2 回完了した後も open のままか）を決める。
FlowValidatorFlowValidator は、統括が返したフローを、実行する前に検査する。フローが検査に通らない場合、FlowValidator は、通らなかった理由をすべて集めて返す。
UnionCheckerUnionChecker は、rebase の衝突を解決した結果に、両方のブランチの変更が残っているかを判定する。
VerifySelectorVerifySelector は、ステージごとに実行する検証コマンドを選ぶ。TestGen と TestFix は軽い検査だけ、ConfirmRed はタスクのテストと軽い検査、Gate はタスクのテストと軽い検査、IntegrationCheck は軽い検査と回帰テストを選ぶ。同じコマンドが 2 つの種類に出たら、先に出た種類で 1 回だけ流す。ConfirmRed は、タスクのテストが落ち、軽い検査が通るときだけ通る。
ガードの規則（guard.py）ガードの規則は、LLM のステージが worktree の中で書いてよい範囲（WriteScope）と、場所が決まらない書き込みを止めるかを決める。worktree の外への書き込みと gh・git push は止めず、最初の指示（system_rules）で禁じる。
wake_for（supervision.py）wake_for は、イベントを受け取り、起動する LLM の統括と、起動の理由（Notice）を返す。wake_for の分岐に無いイベントでは、wake_for は統括を返さない。そのため、ステージが予定どおり進んでいる間は、どの統括も起動しない。
housekeepinghousekeeping は、clean、purge、driver の再実行を今行ってよいかを判定し、行えない場合は理由を返す。clean は、ランの worktree を外し、ランの記録は残す。purge は、worktree と手元のブランチとランの記録を消す。どちらも、GitHub の PR とリモートのブランチは消さない。行えない理由の例は、前の driver が起動した子プロセスがまだ動いていることである。

8. 値オブジェクト

値オブジェクトとは、id、状態の名前、ブランチ名など、1 つの意味を持つ値を型として表したオブジェクトである。値オブジェクトは不変である。列挙の値オブジェクトは Enum で、それ以外の値オブジェクトは frozen=True の dataclass なので、作った後に属性に値を代入すると、Python が例外を投げる。2 つの dataclass の値オブジェクトを == で比べると、dataclass が作る __eq__ が、それぞれのフィールドの値どうしを比べる。たとえば、別々に作った 2 つの TaskId は、どちらも値が task3 なら等しい。

値オブジェクトは、作るときに値の形を検査する。形の検査を持つ dataclass の値オブジェクト（Text と Number を土台にしたものなど）は、形が不正な場合にその場で InvalidValue（ValueError の子クラス）を投げる。Enum の値オブジェクトに定義されていない値を渡すと、Python が ValueError を投げる。どちらの場合も、不正な値を持つ値オブジェクトはできない。集約の状態を見ないと決められない検査（すでに使った番号と重ならないか など）は、値オブジェクトではなく、集約の handle が行う。

分類代表例と、知っておくこと
識別子ExecutionId は、タスク、ステージ、ラウンド、試行の回数を組み合わせた id である。1 つのタスクができてから終わるまでの間に、2 つの実行が同じ ExecutionId を持つことはない。CommandId は、ポリシーと反応がコマンドを送るときに、受け取ったイベントの id と、ポリシーまたは反応の名前から決まる。
列挙列挙は、決まった値のどれか 1 つを取る値オブジェクトである。EscalationKind は、エスカレーションを送る理由の種類を表す（stall、design-gap、needs-replan、supervisor-failed など）。Rating は、指摘の重み（must-fix、should-fix、nit）を表す。
複数の値の組TaskSpec はタスクの中身を表し、件名、完了の定義、受入条件、範囲、入口、境界の形、タスクのテスト（taskTests）を持つ。Decision は回答を表し、回答の文面と、回答した者（ユーザーかラン統括か）を持つ。Issuer は、コマンドを送った者を表す。Issuer は driver が記録するので、ステージや統括は Issuer を自分で指定できない。
上限ParallelLimit は、running と escalated の実装タスクの数の合計の上限を表す値オブジェクトで、既定は 3 である。ほかの上限は値オブジェクトではなく、limits.py の int の定数である。limits.py は次の上限を定める。タスクを 1 本もスタックに追加しない再計画は、2 回までである。指摘は、修正するステージが 2 回完了した後も open のままなら停滞になる。設計のラウンドは 5 回までである。GitJob をキューへ戻すのは 2 回までである。同じイベントをきっかけに起動したタスク統括が続けて判断を返さなかった場合、ラン統括が自分の判断だけで回答してよいのは 2 回までである。2 回を超えると、ラン統括はユーザーの回答を添えて回答する。

9. イベントソーシング

イベントソーシングとは、状態そのものを保存せず、状態を変えたイベントを追記していく方式である。autodev が正しいとみなす記録は、events.db に追記したイベントだけである。autodev は、集約の状態をどこにも保存しない。

再生とは、ストリームのイベントを最初から順に集約の apply に渡し、集約の状態を作り直すことである。driver は、起動したときと、処理の途中で例外が起きたときに再生する。status --json も、状態を表示する前に再生する。

不変条件とは、集約がどの時点でも守る規則である。handle は、コマンドを受理しても不変条件が成り立つかを確かめる。

  • handle は、集約の状態を変えず、I/O も行わない。handle は、HEAD やセッション id を自分で調べない。実行器がそれらを調べて BeginStage コマンドに入れて送る。時刻も、driver はドメインに渡さない。イベントストアが、イベントを追記するときに時刻を付ける。そのため、テストは I/O 無しで規則を検査できる
  • 集約の状態を変えるメソッドは apply である。driver は、再生のときに apply だけを呼び、handle を呼ばない。そのため、handle は、規則で決めたこと（cursor が次に指す位置など）をすべてイベントに書き込む。apply は、イベントに書かれた値をそのまま状態に当てる
  • 集約は、状態を変えるコマンドを受け付けたら、必ずイベントを返す。イベントにしない変化は、再生したときに失われる
  • イベントストアは、追記する前に集約のバージョンを確かめる。集約のバージョンとは、その集約のストリームに追記したイベントの数である。handle した時点の集約のバージョンと、イベントストアにあるストリームのバージョンが違う場合、イベントストアはイベントを 1 つも追記しない。この照合は、handle の後にイベントストアが同じストリームへ別のイベントを追記していた場合に、古い状態をもとに決めたイベントを書き込まないためにある
  • 集約は、拒否（Rejected）と ResultRefused を区別する。形が誤っているコマンド（回答が空である など）と、そのコマンドを送ってよい者でない者が送ったコマンド（判定するステージでない者が送った判定 など）は拒否になり、集約はイベントを返さない。拒否したコマンドは events.db に入らず、ランの記録の logs/rejected.jsonl に理由と一緒に残る。ステージの結果の中身に問題がある場合は、集約は ResultRefused というイベントを返す。Task は、ポリシーを通して ResultRefused を受け取り、result-refused という種類のエスカレーションを送る
